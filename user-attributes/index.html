用户属性 Object / Object Array 扩展

用户属性体系从 5 种基础类型扩展为 7 种，新增 OBJECT 与 OBJECT_ARRAY 类型，支持一对多结构化数据的存储与查询。 覆盖"用户 × 多设备""用户 × 多订单"等场景，复用现有 Liquid 操作链做变量取值，改动控制在最小范围。

文档版本 · V1
设计原则 · 底层 Liquid · UI 可视化 · 运营零代码
更新日期 · 2026-06-09

1. 背景与目标

1.1 背景

EngageLab MA 当前用户属性支持 5 种基础类型：STRING、NUMBER、BOOL、DATETIME、LIST。 随着客户业务复杂度提升，出现大量"一个用户关联多个结构化子实体"的诉求，典型如：

  • 智能安防：一个用户绑定多台摄像头，每台有独立的 device_id、mac、型号、激活时间、AI 套餐状态。
  • 电商：一个用户有多个收货地址、多张优惠券、多笔订单。
  • SaaS：一个用户加入多个工作空间，各自有不同角色和订阅状态。

当前用 LIST 类型存储多设备 mac 列表虽可行，但多个扁平 LIST 之间无法保证同对象关联—— 例如筛选"型号为 A31S_AK_IPC 且 激活时间在 2026 年"的设备时，可能跨设备错配（条件 A 命中了设备 1，条件 B 命中了设备 2，但实际上没有任何一台设备同时满足两个条件），导致分群结果不准确。 这是当前架构的根本性局限。

1.2 目标

  1. 新增 OBJECT 与 OBJECT_ARRAY 两种用户属性数据类型，支持结构化 JSON 数据的存储，并在属性定义时对子字段进行预定义。
  2. 条件筛选支持对象数组子字段的同对象匹配语义，解决扁平 LIST 的跨对象错配问题。
  3. 复用现有 Liquid 操作链模式做变量取值，不发明新交互，仅在操作下拉中新增若干选项。
  4. 最大化复用现有能力（编辑变量弹窗、旅程筛选器、属性预定义流程），把改动控制在最小范围。

1.3 设计原则

底层 Liquid · UI 可视化 · 运营零代码

所有取值逻辑最终都是 Liquid 表达式（where / map / json / sort / first 等），UI 只是让运营通过下拉选择来组合操作链，预览区实时生成 Liquid，不需要手写代码。

1.4 筛选与变量的区别

本方案涉及两种不同场景，引擎和能力边界不同，需注意区分：

场景属性筛选（旅程条件）属性变量（消息取值）
引擎服务端查询引擎Liquid 模板引擎
选择粒度选到子字段（级联选择器第三级）OBJECT_ARRAY：选到属性本身，然后用操作链处理
OBJECT：选到子字段（单个对象无需 where / map）
运算符范围子字段类型对应的全部运算符（等于/大于/小于/包含/正则/时间范围等）where 仅支持等值过滤（Liquid 语言限制）
数据类型限制无限制，各类型运算符齐全DATETIME / NUMBER 的大于小于等比较无法在 where 中使用，需在旅程筛选层面提前过滤

2. 名词定义

术语定义
OBJECT 属性值为单个 JSON 对象的用户属性，如 {"city": "上海", "level": "VIP"}。创建时需要预定义子字段（字段名与类型）。
OBJECT_ARRAY 属性（对象数组）值为 JSON 对象数组的用户属性，如 [{device_id, mac, ...}, ...]。数组中每个对象结构相同，共用同一套子字段预定义。
同对象匹配在对象数组上做多条件筛选时，所有条件必须命中同一个对象，不允许跨对象错配。
识别字段（Identifier Key）对象数组中每个对象的唯一标识字段（如 device_id），可选配置。设置后支持细粒度增删改。
操作链编辑变量弹窗中，运营通过链式叠加操作（where → map → json）组合 Liquid 表达式的交互模式。现有能力，本方案直接复用。
子字段预定义创建 OBJECT / OBJECT_ARRAY 属性时，预先定义其内部子字段的名称和类型。与现有属性预定义流程一致，扩展为支持子字段定义。

3. 用户场景

核心 Push 跳转设备播放页

旅程筛选 devices 有 A31S_AK_IPC 型号 → 推送 → 附加字段带 device_id → 客户端跳转该设备播放页。 操作链：where → sort → reverse → map → first

核心 InApp 按设备组展示内容

旅程筛选 activated_year=2024 → 附加字段带 target_macs（JSON 数组）→ 客户端按 mac 列表决定展示内容。 操作链：where → map → json

扩展 多设备用户分流

旅程条件分支 → devices 对象数 > 1 → 多设备文案分支 vs 单设备分支。在旅程层面处理，不需要变量取值。

扩展 设备到期提醒

筛选 AI 套餐到期时间在 7 日内的设备 → 推送提醒 → 附加字段带过期设备列表。运营在编辑变量中叠加多个 where 条件。

典型场景（智能安防）

用户有 4 台设备：卧室（26 年激活 + AI 套餐）、花园（26 年 + 无 AI）、厨房（24 年 + AI）、书房（24 年 + AI）。

  • 旅程分支 1：activated_year=2026 且 has_ai_package=true → 匹配卧室 → 推送 A 内容
  • 旅程分支 2：activated_year=2026 且 has_ai_package=false → 匹配花园 → 推送 B 内容
  • 旅程分支 3：activated_year=2024 且 has_ai_package=true → 匹配厨房 + 书房 → 附加字段 target_macs = {{ devices | where: 'activated_year', '2024' | where: 'has_ai_package', true | map: 'mac' | json }} → 客户端收到 ["33:44:33","44:55:44"] → 展示 C 内容

4.2 数据上报与更新

4.2.1 写入语义

类型首期后续
OBJECT局部合并（merge）：只传的子字段更新，其他不变；传 null 删除子字段—
OBJECT_ARRAY整体覆盖（replace）：每次写入替换整个数组基于识别字段的 add / remove / update

4.2.2 REST API 示例

API 入口：POST /restapi/user/property，复用现有协议。通过 type 字段区分操作。

① OBJECT_ARRAY：type="set" — 整体覆盖

整个数组被传入值替换。如需保留已有对象，客户端需先拉取全量再合并后上报。

{
  "euid": "user_123",
  "type": "set",
  "properties": {
    "devices": [
      {"device_id": "A001", "mac": "11:22:11", "model_id": "A31S_AK_IPC",
       "activated_year": "2026", "has_ai_package": true, "bind_time": "2026-03-15 00:00:00"},
      {"device_id": "B002", "mac": "22:33:22", "model_id": "VI_STREAM",
       "activated_year": "2024", "has_ai_package": false, "bind_time": "2024-06-01 00:00:00"}
    ]
  }
}

② OBJECT：type="set" — 局部合并

只传的子字段更新，未传的子字段保持不变。

{
  "euid": "user_123",
  "type": "set",
  "properties": {
    "home_address": {"city": "上海", "district": "浦东"}
  }
}

③ 删除属性：type="delete"

{
  "euid": "user_123",
  "type": "delete",
  "properties": {"devices": null}
}

④ 后续：基于识别字段的细粒度操作

后续启用识别字段后，支持通过识别字段定位单个对象做增删改。

// 新增单个对象（按识别字段 device_id 判断是否存在，不存在则追加）
{
  "euid": "user_123",
  "type": "add_object",
  "properties": {
    "devices": {"device_id": "C003", "mac": "55:66:55", "model_id": "PTZ_X1", ...}
  }
}

// 按识别字段删除单个对象
{
  "euid": "user_123",
  "type": "remove_object",
  "properties": {
    "devices": {"device_id": "B002"}
  }
}

SDK 各端参照以上 REST API 的 type 和 properties 结构实现即可。

4.3 条件筛选 · 同对象匹配

所有涉及用户属性筛选的位置均需支持对象数组的子字段筛选：

  • 旅程条件分支（用户特征筛选）
  • 旅程开始组件（用户特征筛选）
  • 事件触发组件（事件触发时，也可以筛选用户属性作为附加条件，此处同样需要支持）

核心语义

用户至少有 1 个 devices 对象同时满足以下所有条件 → 命中

避免跨对象错配：例如用户有两台设备，设备 1 是 A31S_AK_IPC 型号（2024 年激活），设备 2 是 VI_STREAM 型号（2026 年激活）。筛选"型号为 A31S_AK_IPC 且 2026 年激活"时，不应该命中该用户（没有任何一台设备同时满足两个条件）。

筛选交互：复用现有级联选择器

选择对象数组属性时，使用现有的多级级联选择器，在选择对象数组属性后，下一级继续选择其子字段。最终对子字段使用已有的运算符。

运算符

子字段的运算符直接复用该类型已有的全部运算符，无需单独定义。STRING / NUMBER / BOOL / DATETIME / LIST 各自已有的全部运算符均可用。

支持的运算符：为空（用户没有任何对象）、不为空（用户至少有 1 个对象）

4.4 变量操作链

完全复用现有「编辑属性 → 链式操作 → 预览」模式。以下场景展示如何使用已有 Liquid 操作配置对象数组属性的取值。

4.4.1 属性选择说明

OBJECT_ARRAY（对象数组）：选择对象数组属性本身（如 devices），操作链起点是整个数组。where 决定"筛选哪些对象"，map 决定"取哪个子字段的值"。

OBJECT（单对象）：直接选到子字段（如 home_address → city），无需 where / map，结果就是该子字段的值。

4.4.2 可用操作一览

以下操作均为 Liquid 标准能力，已在系统中支持。对象数组场景下配合使用即可：

操作名参数Liquid 语法用途
where字段名, 值| where: 'model_id', 'A31S_AK_IPC'按子字段等值过滤（仅支持等值）
map子字段名| map: 'mac'提取某个子字段，得到值数组
sort子字段名| sort: 'bind_time'按某子字段升序排列
reverse无| reverse反转数组（配合 sort 实现降序）
first无| first取第 1 个元素
last无| last取最后 1 个元素
join分隔符| join: ','将数组拼接为字符串
slice起始位, 长度| slice: 0, 3取子集
json无| json输出为 JSON 格式
default默认值| default: ''空值兜底

ⓘ交互说明：每行 value 右侧增加 {/} 按钮。点击后调起编辑变量弹窗，配置完成后在 value 输入框内以标签块展示（仅显示属性名称，点击可编辑详情）。运营也可以直接手写 Liquid，两种方式并存。

  "nativePage": "album_page",
